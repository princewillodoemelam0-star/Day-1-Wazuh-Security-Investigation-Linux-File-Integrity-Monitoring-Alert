1. Incident Overview

During a routine security monitoring exercise, I received an alert from my Wazuh SIEM dashboard titled "Integrity checksum changed."

The alert indicated that a monitored Linux system had experienced a modification to an important system configuration file.

As a SOC analyst, I wanted to understand what had changed, which endpoint generated the alert, whether the modification was expected, and whether it could indicate unauthorized activity.

I began by reviewing the alert summary, agent information, rule details, MITRE ATT&CK mapping, and the full event log.

3. Understanding What Triggered the Alert

After opening the alert and examining the full log, I discovered that the affected file was:

"/boot/efi/EFI/ubuntu/grub.cfg"

This file is associated with GRUB, the bootloader used by Ubuntu Linux systems.

GRUB plays an important role in the system startup process. Unauthorized modifications to bootloader configuration files could potentially affect how a machine starts or create opportunities for persistence.

The Wazuh log reported:

- File: "/boot/efi/EFI/ubuntu/grub.cfg"
- Event: Modified
- Monitoring mode: Scheduled
- Changed attribute: Inode
- Previous inode: 848
- New inode: 858
- File size after modification: 112 bytes
- Owner after modification: root
- Group after modification: root
- User ID: 0
- Group ID: 0
- Modification time recorded: 2026-06-10 10:12:30

The important observation was that the inode changed from 848 to 858.

An inode identifies a file within a Linux filesystem. A changed inode can indicate that a file was replaced or recreated rather than simply edited in place.

This made the event worth investigating further.

4. Step-by-Step Investigation

Step 1: Alert Identification

I first identified the alert in the Wazuh dashboard.

The alert was generated by Rule ID 550 at Level 7.

I classified it as a medium-severity file integrity alert requiring investigation.

My first objective was to establish whether the event was expected system activity or an indication of unauthorized file modification.

Step 2: Endpoint Identification

I reviewed the agent information.

The affected endpoint was:

- Hostname: ip-172-31-46-166
- Agent ID: 002
- IP Address: 172.31.46.166

I confirmed that this was the endpoint reporting the integrity change.

I also recorded the Wazuh manager as "ip-10-60-2-97".

At this stage, I had identified the monitored machine, but I had not established who or what modified the file.

Step 3: File Identification

I examined the full log to identify the affected file.

The file was:

"/boot/efi/EFI/ubuntu/grub.cfg"

I considered this important because GRUB is involved in the Linux boot process.

A change to this file should not be ignored without confirming whether it resulted from an authorized system update or administrator activity.

Step 4: File Integrity Analysis

I examined the file attributes reported by Wazuh.

The most important finding was:

Old inode: 848
New inode: 858

This indicated a change in the file's filesystem identity.

Wazuh also recorded the file's MD5, SHA1, and SHA256 values after the event.

Step 5: MITRE ATT&CK Mapping

Wazuh displayed the following MITRE ATT&CK mapping:

- Technique ID: T1565.001
- Technique: Stored Data Manipulation
- Tactic: Impact

This technique describes situations where an adversary manipulates stored data to affect the integrity of information.

In this investigation, the mapping helped me understand the potential security implications of an unauthorized configuration-file modification.

However, a MITRE mapping does not prove that an attacker performed the action. It is a classification to guide investigation.

Step 6: Investigation of Possible Causes

I considered several possible explanations:

1. A legitimate Ubuntu or GRUB package update.
2. An administrator modifying the bootloader configuration.
3. A system maintenance operation recreating the file.
4. An unauthorized user or process modifying the bootloader configuration.
5. A malicious attempt to manipulate the system's boot configuration.

I would not classify this as malicious until I had investigated the system's activity around the event.

Step 7: Further Investigation Commands

To validate the alert, I would use the following commands on the affected Linux endpoint.

Check file details:

"sudo stat /boot/efi/EFI/ubuntu/grub.cfg"

Calculate the current SHA256 hash:

"sudo sha256sum /boot/efi/EFI/ubuntu/grub.cfg"

Check the file's ownership and permissions:

"ls -l /boot/efi/EFI/ubuntu/grub.cfg"

Check recent system logs:

"sudo journalctl --since "2026-11-17 18:00:00" --until "2026-11-17 19:00:00""

Check package-related activity:

"sudo grep -iE 'grub|upgrade|install' /var/log/dpkg.log"

I would also review authentication logs, sudo activity, auditd records (if enabled), process execution logs, and other Wazuh alerts associated with the same endpoint.

These checks would help determine whether an authorized administrator, package manager, or potentially unauthorized process made the change.

5. Containment and Remediation Recommendations

If the modification is confirmed to be unauthorized, I would recommend the following actions:

1. Escalate the incident to the appropriate security or system administration team.
2. Preserve relevant logs and file metadata for investigation.
3. Identify the process, user account, or administrative action responsible.
4. If there is evidence of active compromise, isolate the affected endpoint using an approved containment procedure.
5. Review the GRUB configuration against a trusted version.
6. Restore the configuration from a verified backup or trusted package source if it has been compromised.
7. Investigate possible persistence mechanisms and other unauthorized changes.
8. Review user privileges and strengthen access controls.
9. Verify the file's integrity after remediation.
10. Continue monitoring the endpoint for repeated integrity changes.

I would not immediately delete, replace, or restore the file without validating its current state and preserving evidence.

6. Investigation Findings

Based on the Wazuh alert, I established the following:

- A monitored Ubuntu endpoint generated a file integrity alert.
- The affected endpoint was "ip-172-31-46-166".
- The affected file was "/boot/efi/EFI/ubuntu/grub.cfg".
- Wazuh reported that the file had been modified.
- The inode changed from 848 to 858.
- The event was detected during scheduled monitoring.
- Wazuh associated the event with MITRE ATT&CK T1565.001.
- The alert did not provide an external source IP, responsible process, or confirmed user attribution.
- The available evidence was insufficient to establish whether the change was malicious.
